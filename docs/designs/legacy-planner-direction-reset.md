## Problem Statement

Umamusume hides inheritance mechanics behind a three-icon affinity rating. Before a career
run you pick two parent veterans, each carrying their own two parents, and the sparks they
pass depend on Individual Affinity the game never shows. The intent was an open-source tool
that reads a trainer's own roster export and answers what the game refuses to: which
parents to actually pick.

Every candidate answer generated during the session was then found to already ship in
`breeding-optimizer.rappy.dev`.

## What Makes This Cool

One live candidate survives, and it came from the cross-model reviewer: **the
differentiator may be the index, not the scoring model.** "Index" here means a fast,
queryable, fully-expanded view over your own 260 units — every id resolved to a name, every
spark and pedigree field filterable — as opposed to a calculator you feed two picks into.
The user's own choices point the same way: they picked roster search and rejected the
recommendation engine.

This is a hypothesis, not a finding. `breeding-optimizer` has an Inventory tab that may
already be exactly this. Tonight decides.

**Resolved 2026-09-09: the hypothesis held.** Step 1's blocker was the picking surface, not
the scoring model — "too many units without clear indicators of their strengths,
particularly heritage compatibility and the probability of passing specific whites." The
scoring exists downstream of a pick already made, so candidates get pulled into the
calculator one at a time instead of the list saying who is worth pulling.

## Constraints

- Two user-provided inputs: `master.mdb` (~16 MB SQLite) and a roster export. Both
  gitignored; both exist in no commit and no remote.
- Stack committed in README: React + Vite, NestJS, npm workspaces, plain CSS Modules. No
  Tailwind.
- Goal confirmed twice: open source / community tool. Distribution and onboarding are
  design constraints, not afterthoughts.
- The roster export is produced by an external toolchain (UmaExtractor, horseACT). Getting
  a user's data in is not a problem this project controls.

## Premises

1. **Roster import is not a differentiator — and it is the hard part.** Initially closed as
   "not a differentiator" and moved past. That was backwards: it is not a differentiator
   *because* it is the expensive piece, gated on an external extractor toolchain.
   **Implication not to lose:** all three A-directions sit downstream of this, so a
   confirmed gap may still be unbuildable for the intended audience.
2. **Per-spark activation odds are not a differentiator.** Multiple tools display them.
3. **CORRECTED 2026-09-09 — build-target-weighted *ranking* is unserved; *scoring* is not.**
   Originally recorded as "not a differentiator: `breeding-optimizer` ships it as Desire
   sparks." Verified by use during Step 1, and that was wrong. **Desire sparks is a display
   and tuning control, not a ranker:** it highlights wanted sparks on the lineage tree and
   sets each spark's tier (○ / ◎ / gold), which changes the base value feeding Inherited%.
   It answers *how good is this pair for my target* once a pair is picked. It does not
   answer *which of my 260 units are even worth picking*. Those are different questions and
   only the first is served.
4. **Two-sided planning (owned + borrowed) is not a differentiator.** Its Sandbox tab has
   "Add by Trainer ID (uma.moe)"; its Breed Optimizer tab has a "Toggle Sandbox?" switch
   that includes those umas in the pairing sweep.
5. **Borrowing is central to real play.** Free once daily, three times daily total, across
   15+ friend slots; the meta is borrowing strong legacies from top players. User-supplied,
   independently verified.
6. **The training-history half of the export is unused by every tool checked.** The
   *substrate* is verified: all 260 entries in `data.json` carry `support_card_list`
   (always exactly 6 cards, with `limit_break_count`), `scenario_id`, `route_id`, and a
   `race_result_list` of 11-51 entries, median 29 (`program_id`, `result_rank`,
   `running_style`, `popularity`, `weather`, `ground_condition`) — a per-unit race history
   substantially richer than a single career's fixture list. What is **unverified** is
   whether any tool uses it —
   basis is an inspection of six `breeding-optimizer` tabs (Inventory, Sandbox, Breed
   Optimizer, Affinity Checker, Settings, Create Uma) in their empty state.

## Cross-Model Perspective

An independent reviewer (fresh context, no access to the conversation) returned:

- **Coolest unconsidered version:** plan the next *three* runs, not the next pair. A run's
  output becomes the next run's parent, so the real question is what sequence converts the
  current roster into a target unit. Every tool evaluates one run in isolation.
- **The tell:** the user chose "find the parent fast" and rejected the recommender. The
  differentiator is the index, not the scoring model.
- **Prior art:** `SSHZ-ORG/hakuraku`, `CNA-Bld/cjedb`, `SimpleSandman/UmaMusumeAPI` already
  do maintained master.mdb extraction. The roster-reasoning half is what remains.
- **Biggest unexamined assumption:** that getting `data.json` is free. It depends on a
  packet-capture toolchain that breaks on patch day and most trainers will not install.
- **Second:** the rental mechanic means one parent slot is often filled from a pool the tool
  cannot see.

## Approaches Considered

### Approach A: Build what nobody built
Three distinct directions, referenced by ID throughout:

- **A1 — Multi-run sequence planning.** What order of runs converts the current box into a
  target unit. Nothing found models sequence.
- **A2 — Dead-weight detection.** Marginal value per unit: if deleted, how much does the
  best achievable score drop? Roster slots are finite and the game charges for them.
- **A3 — Training-recipe archaeology.** Surface the deck, scenario, route and race line that
  produced each unit. Substrate verified present on all 260 entries; usage by other tools
  unverified.

Effort M-L. **Risk High** — inferred from one inspection pass, against a 0-for-4 base rate
on inferred gaps this session.

### Approach B: Verify before committing — **CHOSEN**
Time-boxed evaluation of the incumbent. Effort S. Risk Low, *provided* the conditional
step 5 in Tonight's Plan is treated as optional; that step alone is neither small nor
low-risk.

### Approach C: Contribute to the incumbent — PENDING, not rejected
Add missing pieces to `breeding-optimizer` rather than compete. Cannot be evaluated until
its licence is known, which is an output of Tonight's Plan, not a reason to discard it.

### Approach D: Build it anyway — RULED OUT
Contradicts the community-tool goal; a duplicate is unlikely to find users.

## Recommended Approach

**B — verify before committing.** Approach A was recommended; the user chose B over it, and
B is what this document now recommends. (The Outcome's "no build is recommended" and this
line agree: A was the recommendation *before* B was chosen.)

The reasoning is stronger than the recommendation it overrode: four inferred gaps died in
one session, so a fifth should not be built on. Ten minutes of real use surfaces what no
amount of UI inspection produces.

## Success Criteria

For the verification step, not a build:

- **Name a gap that blocked or materially slowed the named task in Step 1.** Not "one thing
  it does badly" — every tool fails that bar.
- A recorded *possible / awkward / absent* verdict for each of A1, A2, A3.
- A yes/no on the licence.
- **A rough onboarding verdict — trivial / installable / prohibitive.** This qualifies any
  gap found: per Premise 1, a confirmed gap sitting behind a prohibitive extractor is not
  buildable for the intended audience, and that outranks how good the gap is.
- **If a gap is found:** the next hop is a second office-hours session scoped to that single
  direction, not a build. The 0-for-4 base rate applies to newly-found gaps too.
- **If no gap is found:** the honest outcome is not building this. That is a successful
  result for the evening and the correct place to stop.

## Distribution Plan

Deferred. One constraint is already load-bearing:

- **Data onboarding is the binding constraint, not hosting.** Anything built here inherits
  the UmaExtractor / horseACT dependency.

The client-only-vs-backend question is genuinely open, and the README's objection is
substantive rather than stylistic: *"the game's master database is a 16 MB SQLite file.
Shipping it to the browser is not viable, so the API owns it."* A client-only build is only
possible if the 16 MB is replaced by a pre-extracted slim derived dataset — which is exactly
what `hakuraku` and `cjedb` already do. That, not taste, is what decides whether NestJS
stays.

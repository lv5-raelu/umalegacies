## Problem Statement

A player loops white sparks: they breed until more and more of the six ancestors carry the
same set (Uma Stan, Nimble Navigator, Racing Spirit: Stamina, Tail Held High, Ramp Up), because
more carriers raise both the chance a spark activates during the run and the chance the
trainee comes out carrying it. Each added spark makes the loop harder to complete, so players
end up with several *versions* of one loop. A user asked to see those versions side by side
"without having to switch breakdowns and memorize the differences in skills or star count."

Every surface in the app today explains exactly one pair: the roster's "The pair" pane
(`packages/web/src/roster/ComparePane.tsx`, which despite its name shows one pair), the
search's `PairDetail` dialog, and the `/tree` breakdown. Comparing means opening one,
remembering it, opening the next.

**Real data shows why names cannot do this job.** On the builder's roster (2026-10-09), the
three most alike of their 53 Oguri Caps, each paired with their top Tamamo Cross for a
Mejiro Ryan trainee, read **Oguri Cap / Inari One / Mayano Top Gun** in every P1 slot and
score an **identical pair total of 284**. Only the veteran scores (18571 / 18461 / 18555) and
the sparks tell them apart.

## What Makes This Cool

**A row that opens across every pair at once.** Click Racing Spirit: Stamina and each column
unfolds into its six ancestor slots. In the real example, A and B both show
`P1 3★ IA 213 28%` and C shows `P1 —`: the Oguri Cap herself lost the spark, which is the
whole story of why C reads 39% where A and B read 68%. Nothing on screen says so. The
numbers say it, and the player reads it. That is the instrument the builder asked for: a
lineage laid open for inspection, not a recommendation engine.

## Constraints

- **No verdict, and no emphasis either.** Ruled out during the session: per-row "higher" marks,
  a written gains/losses changelog, and a user-picked lens that ranks pairs. The builder chose
  "bare numbers, no emphasis" against the recommendation, on the grounds that "we cannot know
  for sure what the user wants".
- **DESIGN.md is binding.** It needs five amendments for this surface (see Recommended Approach).
- **Domain logic stays in `packages/core`.** The page renders, it does not compute affinity.
- **Never identify a veteran by character name alone** (255 of 259 share one).
- **Client storage is IndexedDB, not localStorage**, and is disposable.

## Premises (agreed 2026-10-09)

1. **One trainee for every column.** Every number is relative to the trainee, so changing it
   recomputes every column. A pair the new trainee makes illegal (shares a character with a
   parent) keeps its column and says why, rather than vanishing.
2. **The unit is a whole pair**, not a half. Each half is identified by score, its own
   blue/pink/green sparks, and its two parents. When a side is the same pick as a side of an
   earlier column, in either position, the header says so ("same half as A·P2"). That is
   identity, not a rating.
3. **Bare numbers.** No winner, no marks, no summary, no colour that points anywhere. Rows
   align by spark in an order that does not depend on any pair: the groups of
   `SPARK_GROUP_ORDER` (`packages/web/src/lineage/sparks.ts`: blue, pink, green, race, the
   white skills split by firing timing, any untimed white skill, scenario), then by name
   within a group. An absent spark is an em dash.
4. **"Hide rows identical in every pair" is a filter, not emphasis**, on by default. The
   reader's filtered sparks are always shown, first, even when identical or absent everywhere.
5. **Each cell is stars · carriers 0-6 · activate · inherit.** One page-wide window switch
   (1 inspiration / at least once / at least twice) moves activation only. The column header
   carries pair total, base + bonus, and rank.
6. **At most four columns.** On narrow screens the table scrolls inside its own region with
   the spark-name column pinned. The page body never scrolls sideways.
7. **The tray holds pairs of `ParentPick`s inside the persisted selection record**
   (`CachedSelection`, `roster/selection.ts`), beside the picks it already stores. The
   IndexedDB record is already cleared wherever the roster is dropped; the in-memory tray
   must be reset at the same sites (see Code map), because an own pick is an index into one
   roster.
8. **No new engine code.** A column is one `explainPairLocally` call (~0.4 ms measured once
   the master data is loaded; the first call awaits `loadMaster()`).

## Decisions

- **D1, unit: whole pairs, shared halves marked.** Why: a pair is what the game breeds from
  and what every odds number is computed against; diffing pairs gets half-swaps for free.
- **D2, judgment: bare numbers, no emphasis.** Builder's call, against the recommended
  changelog. Why: priorities differ (pinks, white count, continuing the loop) and the tool
  cannot know them.
- **D3, entry: "Add to compare" from search rows, the pair dialog and the roster pair pane,
  one tray, a `/compare` page.** Why: known pairs live on the roster, found pairs live in the
  search; both must feed it.
- **D4, cells: stars, carriers, activate, inherit.** Why: carriers is the loop's own metric
  and inherit decides whether the loop continues; both are hidden (hover only) on today's chip.
- **D5, approach B: full feature plus synchronized carrier expansion.**
- **Inherit is a career figure and never follows the window switch.** `inheritOnceInCareer`
  is computed from `onceInCareer` (see `ComparePane.tsx:493`); a column that changed it on
  "1 inspiration" would be stating a different quantity under the same label. Its column
  header reads "inherit · career". (Caught by the Codex cold read.)
- **One criteria set for the whole page: `pairCriteria`** (`App.tsx:363`, the search's
  criteria or the roster's, whichever surface the reader last took a pair from). It drives the
  "Your sparks" band, the "Only my filtered sparks" toggle and the gold plan, and it is the set
  the roster pane and `/tree` already use, so a column and the pane can never disagree.
- **The gold plan is per spark, the same rule as the pane**: a white skill's inherit figure
  uses the gold row when a criterion naming its group has `gold: true`, and the white row
  otherwise (`goldGroups` in `ComparePane.tsx`). The same rule applies to every column, so the
  inherit figures across a row answer the same question.
- **No large number on this page.** Four 56px totals would rank the pairs by size alone, which
  is emphasis by typography. Pair totals sit at 18px mono. (Claude design voice; Codex
  proposed the pair count as the large number, which says nothing the reader needs.)
- **No TanStack Table.** Pinning is `position: sticky` and expansion is a `Set<groupId>`.
  Codex suggested it; a dependency for what native CSS and a set cover is declined.
- **A hidden row is counted on screen**: "24 identical rows hidden · show". Hiding is only
  honest if the page says what it hid.

## Cross-Model Perspective

**Codex cold read (Phase 3.5).** Coolest unconsidered version: expand one spark across every
column into the six ancestor slots, "keep every column equally styled, expansion
synchronized, and shared halves explicitly named. This respects 'bare numbers' while making
the numbers inspectable." The revealing quote was "bare numbers, no emphasis": the exciting
part is "building an instrument that lets experienced players inspect their own breeding
experiments." It also caught the inherit-window trap and the need to keep compare state
independent of roster picks (`App.tsx` drops picks a trainee change makes illegal).

**Design voices (after the wireframe).** Both converged on a ruled table: 12px mono cells,
30px rows, sticky header and name column, no cards, columns never re-sorted. Codex: lead each
half with score and its own named sparks, since "Oguri Cap cannot identify these versions."
Claude subagent: "the roster's compare pane turned sideways": the same tick, the same
bracketed inherit, the same window switch, the same two-sided header as the pins, so nothing
on the page is new to read.

## Approaches Considered

- **A, tray-lite** (search-row entry only, in-memory tray, no expansion). Not chosen: a reload
  forgets the pairs and known pairs must be dug out of a search.
- **B, full + carrier expansion.** Chosen.
- **C, baseline ghost column** (pin a baseline; it shadows every pair you view). Not chosen:
  caps at two, against "two (or more)".

Approach B.

### The page, top to bottom

1. **Title line**: "Compare pairs", and "{n} of 4" at 11px.
2. **Controls bar** (not sticky): the existing `TraineePicker` (the same component and state
   as the roster screen, so changing it here changes it there), the window switch (`.views`
   idiom), "Hide rows identical in every pair" (on), "Only my filtered sparks" (off; absent
   when there is no filter). The two toggles combine as AND. Under them, the count of rows
   the identical toggle is hiding from what would otherwise show, with a "show" link.
3. **Header row** (sticky top, on `--paper`, `--rule-strong` bottom rule). One column per pair,
   in the order added, never re-sorted:
   - column letter A-D at 10px, the pair total at 18px mono, `151 base + 133 bonus` at 10px,
     the rank glyph;
   - two stacked sides, P1 and P2, each: parent name (Instrument Sans 13px), score and rank
     badge (mono 12px), **its own blue/pink/green sparks with stars**, and
     `Inari One × Mayano Top Gun` at 11px faint;
   - "same half as A·P2" when that side is the same pick as any side of an earlier column.
     Pick identity: an own pick is its roster `index`; a borrowed pick (release 2, not emitted
     today) compares by its whole `VeteranPackage`;
   - remove (achromatic ×) and "Show breakdown", equal for every column. "Show breakdown"
     calls ONE App action, `takePair(pair, lineage)`: `setPicks(pair)`, `setLineage(lineage)`,
     `navigate(TREE)`, the handoff search already does (`App.tsx:573-587`), which search's
     `onPick` is refactored to call too. `/tree` draws App's single `lineage`, so without the
     handoff it would open the roster's pair, not the column's. `pairFrom` is left as-is so
     `/tree` uses the criteria `/compare` showed. The roster's pair becomes this one, which
     is what "show me this pair" means. No button on blocked, loading or error columns.
     (Eng review, Codex #1.)
   - an unused slot is a dashed `--rule` region reading "Add a pair", linking to `/search`.
4. **Table body.** Name column 200px (120px below 600px, names wrap), sticky left: 3px tick
   (filled for blue/pink/green, outlined for white), name in Instrument Sans 12px. Pair
   columns `minmax(200px, 1fr)`. The page body never scrolls sideways.
   **Scrolling, two regimes (eng review 1B, revised after measurement):**
   - **≥ 1080px viewport: no overflow wrapper at all.** Four columns at their 200px minimum
     plus the 200px name column is 1000px, inside the content width there, so nothing
     overflows and the sticky header pins to the PAGE.
   - **< 1080px: the table scrolls in its own box on both axes**: `overflow: auto;
     max-height: calc(100dvh - <controls bar and header>)`. The box is then the scroll
     container on both axes, so the header pins to its top and the name column to its left.
   - **Not `overflow-x: auto; overflow-y: clip`.** That was the first fix, approved, and it
     does not work: `clip` computes to `hidden` when the other axis scrolls (CSS Overflow 3),
     the wrapper stays a scroll container, and the header scrolls away. Measured in Chrome
     153 on 2026-10-14 with a probe page; the two regimes above were measured in the same
     probe (header and name column both at 0px offset after scrolling). The CSS module
     records why, and the 1080px arithmetic, in a comment: if the 200px column minimum
     changes, the breakpoint changes with it.
   - jsdom does no layout, so both regimes are a QA check at 1280px and 375px. Group bands in 10px uppercase mono: "Your sparks", then each group in
   `SPARK_GROUP_ORDER` that has rows, labelled by `groupLabelOf`. Cells in IBM Plex Mono 12px, right-aligned in fixed
   `ch` slots: `3★` · `4/6` · `62%` · `(41%)`, inherit in `--ink-muted` with the chip's
   bracket idiom. An absent spark is an em dash in `--ink-faint`; a genuine zero is ink. Row
   hover lifts the whole row to `--surface` so the eye can follow it across.
5. **Expansion.** The row label is a `<button aria-expanded>`. Opening it opens that row in
   every column: six lines `P1 · gp · gp · P2 · gp · gp`, each with stars, Individual Affinity
   and per-inspiration rate from `SparkSummaryRow.carriers`, absent slots muted. 200ms
   ease-out, respecting reduced motion; figures never animate.

### States

- **Roster loaded, no trainee chosen**: the controls bar shows the `TraineePicker` and the
  table is absent, with one line: "Choose who you are training." The tray is kept.
- **Per-column loading**: a column whose lineage is being computed keeps its header and shows
  "Explaining…" in place of its cells (the pane's wording); other columns render.
- **Stale master data**: a `StaleMasterError` from any column goes to the app's existing
  banner (`setMasterChanged(true)`, `seenMasterHash` reset, `App.tsx:525-531`), not to four
  copies of one message. (Eng review 1C.)
- **Per-column error**: any OTHER failure (a load failure) is per column: the column keeps its
  header and states the error in place of its cells; nothing else on the page changes.
- **Late results**: the `ComparePage` effect carries a `cancelled` flag exactly as App's does
  (`App.tsx:509, 535-537`), so a slow result for the previous trainee or tray can never
  paint over the current one. Both App and `ComparePage` call ONE shared helper for the
  then/catch (`lineage/explain-local.ts`), so the stale-master rule exists once.
- **Fewer than two pairs**: the one column renders plus "Add a pair" slots; zero pairs means
  the table is absent and the page says how to add one (DESIGN.md: absent, not disabled).
- **No roster loaded**: no redirect. `/compare` joins `/search` and `/roster`, which have no
  guard (`App.tsx:172-176`): with no roster it renders the landing and drop zone, and once a
  roster exists it renders the page. (Eng review 1A. Copying the tree's guard would have
  bounced every reload to `/search` before IndexedDB answered.)
- **Restoring (every route, not just this one)**: while `restoring` is true the shell renders
  its header and nav and NOTHING else: no welcome lede, no drop zone, no page body. Today
  `roster` is null during restore, so every route flashes the landing and the drop zone in
  its `parsing` state (`App.tsx:615`, `640-650`) before the restored page replaces it. The
  builder's call: no glimpse of the drop zone on any reload. If `restoring` is still true
  after ~300ms, one muted line appears: "Restoring your roster…" (eng review D14; DESIGN.md:
  a waiting surface says what it is waiting for). A fast restore shows only the header.
  Test (jsdom, fake timers): resolved at 100ms → no line; at 500ms → the line, then the page. The `/tree` guard
  (`App.tsx:205-208`) also gains the restore gate and asks whether a lineage CAN come (a
  trainee and a full pair exist) rather than whether one has arrived yet, because it runs
  before the explain effect in the same commit and would otherwise bounce a reloaded `/tree`.
  Its comment ("The roster lives only in memory, so a reload...") has been stale since the
  IndexedDB restore landed and is corrected in the same edit.
- **Trainee change**: every column recomputes; a pair now illegal keeps its header and states
  the reason in place of its cells.
- **Tray full**: "Add to compare" says "4 of 4, remove one on /compare" instead of acting.
  It never silently replaces a pair.
- **Duplicate**: adding a pair already in the tray (in either order, A×B = B×A) is a no-op that
  says "already comparing".
- **Roster replaced, forgotten, or master hash changed**: the tray is cleared and `/compare`
  says so once (the `trayCleared` flag, see Code map).
- **No filter set**: no "Your sparks" band and no "Only my filtered sparks" toggle.

### Data flow

```

          │  "Add to compare" (ParentPick pair)
          ▼
 App.tsx  tray: ParentPick[][]  ──writeSelection──▶ IndexedDB (CachedSelection.tray, optional)
   │  ▲                                              │ restoreSelection: index+cardId check,
   │  └──────────── restore (restoring=true) ◀───────┘ NO legality filter, bad/missing → []
   │  trainee, pairCriteria, window
   ▼
 ComparePage effect (cancelled guard; results Map keyed masterHash+trainee+pair)
   for each tray pair whose key is missing from the Map:
     isLegalPair? ──no──▶ { blocked, reason via pickBlock }
        │yes
        ▼
     explainPairRequest → explainPairLocally ──StaleMasterError──▶ App banner (shared helper)
        │ok                                  └─other error──▶ { error, message }
        ▼
     { ok, lineage }
   ▼

                                                        shared-half labels
   ▼

```

### Code map

- `packages/web/src/compare/compare-model.ts`: pure, no async. Input is one entry per tray
  pair, a union: `{ kind: 'ok'; lineage: LineageResponse } | { kind: 'blocked'; reason:
  string } | { kind: 'loading' } | { kind: 'error'; message: string }`, plus `pairCriteria`,
  the window, and `roster.sparkOptions` (eng review, Codex #6): a criterion carries only a
  `groupId`, so a filtered spark absent from every `ok` column takes its name and kind from
  the catalogue, exactly as `ComparePane` does for "a requirement this pair misses"
  (`ComparePane.tsx:135-136`). Test: a criterion no pair carries renders its name, its tick
  and an em dash in every column. Returns aligned rows (union by `groupId` over the `ok` columns; filtered
  sparks first, including any carried by no pair; then `SPARK_GROUP_ORDER` + name), per-cell
  values for the window, the career inherit figure via `inheritOnceInCareer` under the
  per-spark gold rule, an `identical` flag per row (computed over `ok` columns only), the
  hidden count, and shared-half labels. **"Identical" means the PRINTED cell** (eng review
  2B): the four strings the reader sees (stars, carriers, activation in the selected window
  via `percent()`, inherit) match in every `ok` column. Switching the window recomputes the
  flags and the hidden count. Tests: 43.12% vs 43.49% hides; a row differing only under
  "at least twice" reappears when that window is chosen. **The filter needs two finished
  columns** (eng review, Codex #4): it applies only when ≥ 2 columns are `ok` and none is
  `loading`; otherwise every row shows and the toggle is absent (DESIGN.md: absent, not
  disabled). Blocked and error columns do not count. Without this, one pair in the tray is
  "identical in every pair" with itself and the default-on filter hides the whole table.
  Tests: 1 `ok` column → all rows shown, no toggle; 2 `ok` + 1 `loading` → nothing hidden
  until it lands. *Considered and kept (Codex #5):* printed equality can hide a row whose
  carriers sit in different ancestor slots. Kept anyway: the numbers are equal for the
  career being planned, the real three-pair Oguri Cap example had 0 of 74 such rows, and
  the reader can switch the filter off. Unit-tested, including a blocked column.
- `lineage/odds.ts` (NEW, extracted, eng review 2A): `OddsView` and its two label tables,
  `valueFor(row, view)`, `goldGroupsOf(criteria)` and `cellInherit(row, gold)`, moved out of
  `ComparePane.tsx` (lines 59-72, 117-122, 288, 493-498) unchanged. `ComparePane` and
  `compare-model` both import them, so "the pane and `/compare` show the same number" holds
  by construction. `ComparePane.test.tsx` must stay green with no edits to its assertions.
- `compare/ComparePage.tsx` owns the async work: an effect keyed on (trainee, tray) runs
  `explainPairRequest` → `explainPairLocally` per pair, the same path `App.tsx:502-517`
  uses. **Results are keyed, not positional** (eng review, Codex #2): a `Map` from
  `masterHash + trainee card + unordered pair key` to the column union above. Columns are
  DERIVED from tray order plus the Map; a column whose key has no entry renders `loading`,
  never another pair's numbers. The effect computes only keys the Map lacks, so adding or
  removing one pair leaves the other columns' numbers on screen with no "Explaining…"
  flash. Tests: remove A after all have loaded → B and C keep their own numbers and never
  show loading; switch trainee after load → every column shows loading until its own new
  result. Legality is DECIDED by core's
  `isLegalPair` (`packages/core/src/filter.ts:342`: same veteran, either side is the trainee,
  same character); `explainPairRequest` itself checks nothing. `pickBlock` (`filter.ts:359`)
  is used only to WORD the reason (`is-trainee`, `same-uma`), since it returns null early
  for the same veteran on both sides. A blocked pair never reaches `explainPairLocally`.
- `compare/CompareTable.tsx`, `PairHeader.tsx`, `CarrierSlots.tsx`, each with a colocated
  `.module.css` (README convention).
- `compare/tray.ts`: pure tray operations (add, remove, dedupe unordered, cap 4) on a
  `ParentPick` pair list. Persisted as an OPTIONAL `tray` field of `CachedSelection`.
  **Do not bump `CACHE_VERSION`**: it is shared with the roster record
  (`cache-policy.ts:35`), so a bump makes every user re-upload their save and loses their
  trainee, filters and picks. A missing or malformed `tray` restores as `[]`. Restoring
  validates each own pick's `index` + `cardId` the way `restorePicks` (`selection.ts:214`)
  does, but does NOT apply its legality check: a pair the trainee makes illegal stays as a
  blocked column (Premise 1).
- **Clearing.** `App.tsx` calls `setTray([])` at every site that drops or replaces the
  roster: `forget()` (~292-300), a new upload, and the stale-cache path (~236). Otherwise the
  `writeSelection` effect (~483-493) writes the old tray straight back. Each of those sites
  also sets a transient `trayCleared` flag that `/compare` shows once ("Your compare tray was
  cleared because the roster changed") and then resets.
- `route.ts`: `COMPARE = '/compare'`. `vercel.json`: add `compare` to the web rewrite
  `/(search|roster|tree|compare)`.
- Entry points: `search/PairSearch.tsx` rows, `search/PairDetail.tsx` action bar,
  `roster/ComparePane.tsx` (not embedded). `SiteNav.tsx`: a "Compare (n)" item when the tray
  is non-empty.
- `App.tsx` owns the tray beside the picks, **separately from them**.

## Open Questions

1. **Should a filtered spark's NAME be lit (`--ink` against `--ink-muted`)?** The Claude
   design voice proposes it: the highlight is the reader's own choice and touches no number,
   and `ComparePane`'s `chipAsked` does the same. It is still emphasis. The default here is to
   NOT light it: the "Your sparks" band already says which rows the reader asked for.
2. **"Hide identical rows" cuts less than expected.** Real data, with a five-spark filter:
   the three pairs carry 74 distinct sparks, 24 identical in every pair. Four filtered sparks
   are among the other 50 and Ramp Up is carried by no pair, so the page shows 51 rows (5 in
   "Your sparks" + 46 below) and hides 24. Versions of one loop share grandparent
   *names*, not grandparent *veterans*, so they differ almost everywhere. The "Your sparks"
   band and the "Only my filtered sparks" toggle carry most of the organizing. Worth watching
   after release whether players want a third filter (e.g. "only sparks with 2+ carriers in
   some pair", which is still a filter and not a mark).
3. **Blue rows always read 100%.** DESIGN.md says to omit a row that is always 100%, but the
   STARS differ (Power 5★ / 6★ / 7★ in the real example) and blue stars are what the trainee
   gains. Keep them; note the exception in the compare-table component entry.
4. **Borrowed halves are release 2.** `borrowed` is declared on `ParentPick` and never
   emitted today. The tray stores whole `ParentPick`s, so it holds a borrowed package as-is
   when release 2 starts emitting one; nothing else to decide now.

## Test Plan (eng review 3A)

The web tests run in Vitest's `node` environment and render through `renderToStaticMarkup`.
That was the M0 scaffold's default, kept in PR #19 because the first component tests needed
nothing more; it was never a decision against a DOM. This feature's riskiest bugs are WIRING
bugs inside `App.tsx` effects, so the plan is: decisions as pure functions tested in node,
plus a few App-flow tests that opt into jsdom per file with `// @vitest-environment jsdom`.
Every existing test stays in node, untouched.

New dev dependencies (web workspace only, nothing shipped): `jsdom`,
`@testing-library/react`, `fake-indexeddb`.

   AND a gold criterion. Written first, green before and after the `odds.ts` extraction (2A).
2. `shell.test.ts`: `treeShouldRedirect` is false while restoring and false when a trainee and
   a full pair exist but the lineage has not arrived; true when no pair is possible (1A).

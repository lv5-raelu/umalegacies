## Problem Statement

Umamusume shows legacy compatibility as a ◎/〇/△ icon. That icon is the **pair total**
bucketed by `succession_relation_rank` (verified: rank 1 = 0–50, rank 2 = 51–150,
rank 3 = 151–9999), and it is not the same quantity as **Individual Affinity**, the
per-member sum that actually drives spark activation rates. The game shows neither number.

Eleven implementations were examined and all of them show the numbers. Not one shows **where a number came from** — which
succession relations matched, what each was worth, which shared G1 wins counted, and which
rule applied at which link.

**This project claims no market gap and does not need one.** Verified 2026-09-09: the
planning workflow is served by `breeding-optimizer.rappy.dev` (closed) and largely by
`ayaliz/hakuraku` (MIT, and already forked to `lv5-raelu/hakuraku`). Asked directly whether
they would still build if an open equivalent existed, the builder said yes twice — once
hypothetically, and once after being shown that it does exist and is already in their own
account. **The motivation is building it. That is the stated and sufficient reason.**
Success criteria below are written for a thing that gets finished and used, not one that
wins adoption.

## What Makes This Cool

**Every number opens.** An affinity value expands into the `succession_relation` rows that
produced it, each with its `relation_point`, plus the itemized shared G1 wins, with the rule
named. **Caveat that shapes the work: `master.mdb` has no names for relation types.** Only
`succession_relation` and `succession_relation_member` reference `relation_type`, neither
carries text, there are 1616 distinct types, and no `text_data` category comes close to that
count. A bare `relation_type 508, 8 pts, shared by these three charas` is already more than
any tool shows; a labelled `"Kanto region"` requires a community-maintained mapping that is a
dependency of this project, not a lookup. A closed calculator can be trusted, never checked; the open ones checked here all
return bare scalars and throw the reasoning away. `hakuraku`'s `calculateAffinity` returns
`number`. So did the previous implementation in this repo.

The one place provenance already exists anywhere in this space is `hakuraku`'s
`calculateRaceBonus`, which returns `{entries: [{saddleId, name, bonus}], total}`. That is
the shape, applied to one of twelve variables. This project applies it to all twelve.

## Constraints

- Two user-provided inputs: `master.mdb` (~16 MB SQLite, 416 tables) and `data.json` (260
  trained characters). Both gitignored; both exist in no commit and no remote.
- Stack per README: npm workspaces, NestJS API owning `master.mdb`, React + Vite +
  TypeScript, plain CSS Modules. **No Tailwind.**
- Hosted deployment. **Server-side data handling is UNDECIDED** — see Open Questions. An
  earlier draft asserted a never-persist rule; that was the reviewer's invention, not the
  builder's decision, and it has been withdrawn. The resolved roster is cached in the
  browser's own IndexedDB per README; what the server does with an upload is an open call.
- **The repo is empty.** `git ls-files` returns `.gitignore`, `CLAUDE.md`, `README.md`. The
  prior implementation was deleted in the 2026-09-08 reset. Its *knowledge* survives in
  README's Gotchas and in `~/.gstack/projects/lv5-raelu-umalegacies/learnings.jsonl`; its
  *code* does not. This is a greenfield build and Milestone 0 exists to say so.
- **No relation-type name source exists in either input.** 1616 relation types, zero names
  in `master.mdb`. Labelling them is a hand-maintained mapping this project must own,
  scoped into M2 and carried with a `Citation` naming where each label came from. Until it
  exists, nodes render the id, the point value and the matching charas.
- Onboarding ceiling: the roster export needs UmaExtractor or horseACT, rated *installable*.
  `xancia/UmaExtractor` (30★, 10 forks) carries **no licence**, so the toolchain this
  project depends on is itself legally all-rights-reserved. Noted, not solved.

## Premises

1. **The planning workflow is served, twice over.** `breeding-optimizer` (closed) ships
   roster import, Breed Optimizer pair ranking sortable by Inherited% / Run Appearance% /
   Combined%, Desire Sparks tier weighting feeding those numbers, a per-pair modal with the
   lineage tree and per-spark inspiration odds with a full-run toggle, and uma.moe Trainer
   ID import. `ayaliz/hakuraku` (MIT) ships most of the same. **No feature gap justifies
   this project and none is claimed.**
2. **Provenance is the exception.** Every implementation examined, open and closed, returns
   affinity as a scalar. The only counter-example is `hakuraku`'s `calculateRaceBonus`,
   which itemizes G1 wins. Nothing itemizes base affinity.
3. **The reason to build is that the builder wants to build it.** Confirmed twice, the
   second time with an actual MIT equivalent already in their GitHub account. Recorded as a
   preference, not defended as market logic. The same applies to hosted NestJS over a static
   build: it is what they want to write. **Server-side data handling was NOT decided here**
   and any earlier statement of a never-persist rule was the reviewer's, not the builder's.
4. **README goal 3 predates all analysis:** *"Show the reasoning, not just a verdict. Every
   number is traceable back to the relations and race wins that produced it."*
5. **Borrowed ancestors are not a blocker.** Measured on the real `data.json`: 499 of 1556
   ancestor slots (32%) and 114 of 520 parent slots (22%) are borrowed
   (`owner_viewer_id != 0`). Every ancestor entry carries its own `factor_info_array` and
   `win_saddle_id_array` inline, so **no roster lookup is required** to score one. Ancestors
   carry no `trained_chara_id` at all — only `card_id`.
6. **Onboarding is the ceiling and the extractor is unlicensed.** Both true; neither solved
   here.

**Superseded direction, recorded:** the predecessor doc's one demand-backed finding was
*"ranking your own roster by probability of passing a named set of white sparks."* It was
falsified on 2026-09-09 — `breeding-optimizer`'s Breed Optimizer tab ranks pairs and Desire
Sparks weights them by wanted sparks. Its "no build is recommended" outcome is reversed
here on the grounds in premise 3, not on a rediscovered gap.

## Domain Model Corrections

Five errors found in review. Four would have shipped as bugs. The fourth (`card_id`) is
future-proofing: zero of the 52 distinct `card_id`s in this `data.json` are affected, so it
is a trap avoided rather than a bug caught.

1. **Seven base affinities, five bonus affinities — not seven of each.** Bonus affinity is
   +3 per G1 shared between two members that have both raced. The trainee has not raced, so
   the two trainee↔parent links carry a base term only. A uniform 7×{base,bonus} tree
   produces two nodes that can never be non-zero.
2. **`relation_point` lives in `succession_relation`, not `succession_relation_member`.**
   Verified schema: `succession_relation(relation_type, relation_point)` and
   `succession_relation_member(id, relation_type, chara_id)`. A provenance record citing
   only the member table shows membership and not the number's origin, which is the whole
   product.
3. **`succession_relation_member.id` is an arbitrary surrogate and `master.mdb` has no
   version table** (checked all 416 table names). Cite the natural key
   `(relation_type, chara_id)` plus a SHA-256 and extraction date of the `master.mdb` used.
   A cited `rowId` silently rots when a patch renumbers rows.
4. **`card_id` → `chara_id` must go through `card_data`.** The roster and every ancestor
   carry `card_id` (e.g. `101601`); relations key on `chara_id` (`1016`). `id // 100` holds
   for 100 of 102 cards and fails on two (`9100101`→`1001`, `9101101`→`1011`). Join, do not
   divide.

Names come from `text_data` where `category = 6`; its key column is literally named
`index`, a SQL reserved word that must be quoted in every query (`SELECT text FROM text_data
WHERE category = 6 AND "index" = ?`). Win-saddle names are `category = 111` (184 rows, keyed by `single_mode_wins_saddle.id`, and they are epithets like `Classic Triple Crown` rather than race names). The ◎ threshold is
`succession_relation_rank.rank_value_min = 151`.

5. **One lineage in the roster has no grandparents.** `trained_chara_id 8361`
   (`succession_num: 0`) carries only `position_id` 10 and 20. 259 of 260 are complete. Any
   required 4-tuple of grandparents fails on it.

- **B — The full show-your-work planner — CHOSEN.** Roster upload, box browse, tree,

- **C — Corpus and verification harness.** Publish the record format, a dataset, and the

## Recommended Approach

**B**, with the provenance spine first. The keystone is a type, not a screen:

```ts
type NodeKind = 'total' | 'individual' | 'link' | 'base' | 'bonus' | 'row';

interface Citation { label: string; url?: string; quote?: string }  // link out, quote inline, or both

interface MasterRef {
  table: 'succession_relation' | 'succession_relation_member' | 'single_mode_wins_saddle'
       | 'succession_relation_rank' | 'card_data' | 'text_data';
  key: Record<string, number>;   // NATURAL key, e.g. { relation_type: 3, chara_id: 1016 }
  columns: Record<string, number | string>;
}

type RuleId =
  | 'total.pair' | 'individual.member' | 'link.pair'
  | 'base.two_way' | 'base.three_way' | 'bonus.shared_g1'
  | 'row.relation' | 'row.saddle'
  | 'base.absent_ancestor' | 'bonus.absent_ancestor';

interface ExplainNode {
  kind: NodeKind;
  label: string;                 // "Trainee <-> Parent A", "Kanto region", "Yasuda Kinen"
  value: number;
  ruleId: RuleId;                // stable, localizable key; see union below
  ruleText: string;              // human-readable, localizable off ruleId
  citation?: Citation;
  sources: MasterRef[];
  children: ExplainNode[];       // INVARIANT: value === sum(children.value) when non-empty

  // CEO review Issue 1: a 0 from "they share nothing" and a 0 from "I could not
  // resolve this id" must never look alike. This product's whole claim is that a
  // number opens; an unexplained 0 opening onto an empty drawer inverts it.
  resolution:
    | { ok: true }
    | { ok: false;
        reason: 'unknown_chara' | 'unknown_card' | 'unknown_saddle' | 'no_relation_rows';
        id: number };
}

interface AncestorRef {
  cardId: number;                // ancestors carry card_id only, never trained_chara_id
  winSaddleIds: number[];        // inline on the ancestor; matched by RAW id, see below
}

interface ExplainRequest {
  traineeCharaId: number;                    // chara_id from card_data; the trainee has not raced
  parents: [AncestorRef, AncestorRef];                                  // position_id 10, 20
  grandparents: [AncestorRef | null, AncestorRef | null,
                 AncestorRef | null, AncestorRef | null];               // 11, 12, 21, 22
  masterHash?: string;           // OPTIONAL echo of GET /master/meta, for staleness detection
}

interface ExplainResponse {
  pairTotal: ExplainNode;        // kind 'total'; 7 base + 5 bonus; drives the icon rank
  individualAffinity: {          // kind 'individual'; 4 links per parent, 1 per grandparent
    [positionId: number]: ExplainNode;
  };
  relationRank: {                // the icon verdict opens too, but it is a LOOKUP not a sum,
    value: number;               // so deliberately NOT an ExplainNode: value 3 with children
    ruleId: 'rank.lookup';       // summing to 337 would break the sum invariant
    sources: MasterRef[];        // cites the succession_relation_rank row
  };
  rankBounds: { min: number; max: number };   // that row's rank_value_min / rank_value_max
  masterHash: string;            // authoritative; the server owns master.mdb
}

interface ErrorResponse { code: string; message: string; field?: string }  // README: 400, never 500
```

**G1 matching rule: group-normalised. SETTLED by domain knowledge 2026-09-09.** `master.mdb`
records some G1s under several saddle ids sharing a `group_id` (7 such groups; Satsuki Sho is
both 18 and 155). Two readings are possible and they are not decidable from `master.mdb`,
`data.json`, or `hakuraku`:

- **raw ids** — ancestors share a G1 only if the same saddle id appears on both. **WRONG.**
- **group-normalised** — map to `group_id` first, so 18 and 155 count as one race. **CHOSEN.**

**The builder settled it:** *"umas that win the same G1 count towards the +3 bonus affinity
rule, regardless of the year the race was won."* Some races run twice in a career (Arima
Kinen, Takarazuka Kinen), and the data matches that exactly — every `group_id` holding more
than one G1 saddle id holds **the same named race**:

```
group 17  18 = Satsuki Sho         | 155 = Satsuki Sho
group 18  13 = Tenno Sho (Spring)  | 153 = Tenno Sho (Spring)
group 24  14 = Takarazuka Kinen    | 147 = Takarazuka Kinen
group 28  16 = Kikuka Sho          | 148 = Kikuka Sho
group 41  39 = JBC L. Classic      | 156, 159, 162 = JBC L. Classic
group 42  37 = JBC Sprint          | 157, 160, 163 = JBC Sprint
group 43  31 = JBC Classic         | 158, 161, 164 = JBC Classic
```

Multiple ids are the same race won in different years. Matching on raw ids therefore misses a
genuinely shared G1 whenever two ancestors won it in different years.

**This means `hakuraku` is wrong here**, and the port must deliberately diverge from its
oracle. Measured: the two readings differ on **344 of 1295 bonus links** and change
`pairTotal` on **161 of 259 lineages**, by +3 to +15. Fixture 4711 scores 135 bonus under
both, so it cannot detect this; **fixture 7149 exists to**.

**README's stated dedupe rule is dead code.** README says to deduplicate on `group_id`
because "the master data ships several rows for the same race." Measured: **zero** ancestor
slots hold two type-3 saddles from one group. Dedupe-after-selection never fires. README
should be corrected; it describes a problem this data does not have and hides the real
ambiguity above.

**Resolution rules.** An id the *caller supplied* and the server cannot resolve is a `400`
naming the offending id, per README's validate-at-the-boundary convention. An id found
*inside* otherwise-valid data (an ancestor's unknown `win_saddle_id`, a chara with zero
relation rows) renders an in-tree node with `resolution.ok === false`, never a bare `0`.

**One resolver, not three.** `card_id -> chara_id` must go through a single `charaIdFor()`
that joins `card_data`. hakuraku inlines `Math.floor(card_id / 100)` in at least three
functions; porting that shape means fixing Domain Correction 4 in three places and missing
the third.

**A null grandparent** kills both a base and a bonus term, so it contributes *two* zero
nodes (`base.absent_ancestor`, `bonus.absent_ancestor`) and the invariant holds.
`individualAffinity` still emits keys 11/12/21/22 with value 0 rather than omitting them, so
box browse can render a uniform six-slot tree. `trained_chara_id 8361` is the one roster
lineage this applies to; it is detected by `succession_chara_array` position coverage, **not**
by `succession_num`, which is 0 on 135 of 260 entries including the complete fixture 4711.

**`pairTotal` and `individualAffinity` reconcile exactly, and the identity is a required M1
assertion.** Every link is counted by both of its endpoints except the two trainee-parent
links, which have no trainee-side individual, so:

```
sum(individualAffinity) === 2 * pairTotal - base(T,10) - base(T,20)
606                     === 2 * 337       - 33         - 35
```

Verified across all 259 complete lineages in `data.json`: zero violations. This is the
cheapest correctness check in the design and it needs no oracle. (An earlier draft of this
document told the implementer *not* to cross-check them, on the strength of noticing
606 != 337 and stopping there.)

**Routes.** `GET /master/meta -> { masterHash, extractedAt }` (M0; how a client obtains the
hash *before* issuing a request, since the response also returns it), `POST /affinity/explain` (M1), `POST /roster/resolve` (M3), and a
batch explain for box browse (M3). **Size it before building it:** one `pairTotal`
tree averages ~120 leaf rows and `individualAffinity` re-emits most of them, so 260 lineages
is roughly **62,500 leaf nodes** — tens of MB on M3's opening screen. The type has no
interning, no sources-by-reference and no lazy expansion. Return summaries and explain on
demand, or add one of those three.

### Correctness oracle, with its caveats

`hakuraku`'s `src/data/VeteransHelper.ts` (MIT, on disk) is the reference. It is **not**
directly runnable against this project's inputs, and pretending otherwise would produce
false failures at M1:

- **Different data source.** It loads a bundled `data/umdb.binarypb.gz` snapshot, not this
  `master.mdb`. The same objection that demotes `breeding-optimizer` to a secondary check
  applies to it.
- **It derives `chara_id` as `Math.floor(card_id / 100)`** — the thing Correction 4 says not
  to do. Harmless on this data (0 of 52 card_ids affected), but it means the oracle and this
  implementation can diverge on a card neither has seen.
- **It does not dedupe G1s on `group_id`;** it uses a race-instance-ID range heuristic
  because the bundled snapshot omits grade fields. Both rules select the same 47 saddles
  here and never differ across the roster's 1296 bonus links, but 7 `group_id`s do contain
  multiple `win_saddle_type = 3` rows, so the divergence is latent rather than impossible.
- **Incompatible signature.** It takes full `Veteran` records and reads a parent's own
  `succession_chara_array` for the race bonus; `ExplainRequest` passes flat `AncestorRef`s. A
  translation harness is needed and is part of M1's scope.
- **Undocumented quirk to replicate:** when `gpCharaId === targetCharaId` it treats that
  grandparent's relations as empty. This is not rare: **84 of 259 lineages (32%)** have at
  least one grandparent sharing the trainee's `chara_id`, so on roughly a third of the box
  "we agree with hakuraku" partly means "we copied it correctly." Say so rather than calling
  it independent verification.
- **The G1 matching rule is a deliberate divergence.** `hakuraku` matches raw saddle ids and
  is wrong (see Recommended Approach). The harness must **expect** disagreement on exactly
  the links where an ancestor pair's shared G1 sits in one of the 7 multi-id groups, and
  assert agreement everywhere else. That is a stronger test than blanket agreement was: a
  divergence anywhere else is a real bug in the port.

**How to actually call the oracle**, since `hakuraku` has no pair-total function and no rank
bucketing at all:

```
calculateAffinity(p1, T) 157 + calculateAffinity(p2, T) 113 + calculatePairAffinity(p1, p2) 67 = 337
```

`relationRank` has no oracle beyond `master.mdb` itself.

**M1 passes when** this implementation and `hakuraku` agree *given the same relation and
saddle tables extracted from this `master.mdb`*, and the fixture matches the golden numbers
above. `breeding-optimizer`'s reported number is a tertiary sanity check only.

## Milestones

**M0–M2 are scaffolding and are usable by nobody, including the builder. M3 is the first
release anyone can use, and it satisfies the success criterion on its own. M4–M6 are
post-success and optional, ordered by appetite rather than need** — each re-implements a
`hakuraku` file already read (`SparkProcModal.tsx`, `UrlSharing.ts`), so none of them is
required for this project to have succeeded. The graveyard in Prior Art is full of projects
abandoned before their equivalent of M3; reaching it fast is the whole plan.

- **M0 — Scaffold.** npm workspaces, NestJS bootstrap, Vite web app, read-only `master.mdb`
  loading, `GET /master/meta`, the `card_data` join, the CORS allowlist README warns about,
  and the `ErrorResponse` shape. No features.
- **M1 — The spine.** `POST /affinity/explain` and the `ExplainNode` tree for fixture 4711.
  **Deliverables include a committed `fixtures/4711.json`** (the six `AncestorRef`s — public
  game ids only, `owner_viewer_id` stripped) **and a committed slice of the needed
  `succession_relation`, `succession_relation_member`, `single_mode_wins_saddle`,
  `card_data`, `succession_relation_rank` and `text_data` rows** (~350 member rows, 251
  relation rows, 47 saddles, 7 cards, 3 rank rows), carrying a recorded `masterHash`
  constant since no hash is computable from a row slice, so the golden test runs in a clean
  clone and in CI with neither `data.json` nor `master.mdb` present. Also the `hakuraku` translation harness. **Test suite (CEO review Issues 3 and 6).**

*Runs in CI, from the committed slice, with no user files present:* golden fixture 4711
(-> 337 / rank 3 / all twelve link terms); **golden fixture 7149 (-> 460 / rank 3 / bonus
288), which fails under raw-id matching and is the only test that can catch a regression to
`hakuraku`'s rule**; lineage `8361` producing
`base.absent_ancestor` / `bonus.absent_ancestor` zero nodes; the unresolved-id cases emitting
`resolution.ok === false` rather than a bare `0`.

*Runs locally only, by hand:* the reconciliation identity across all 259 lineages (needs
`data.json`, which stays gitignored) and the `hakuraku` translation harness (needs the fork's
source, which lives in an untracked sibling directory). **The doc previously claimed all of
M1's tests run in CI. They do not, and committing a derived slice of the save to make them
was considered and declined.**

*Correction:* the identity is an **accounting tautology**, not a correctness test. Both sides

## Open Questions

1. Cite community research inline or link out? The `citation` field supports both; inline is
   more auditable and dates faster.
2. What happens when a game patch changes `master.mdb`? `GET /master/meta` gives the client
   a hash to echo, so staleness is *detectable*. Not answered: what the UI does about it, and
   whether old permalinks re-resolve or are rejected.
3. **What does the server do with an uploaded `data.json`?** Genuinely undecided. Options
   run from parse-and-discard, through a short-lived cache keyed by content hash, to storing
   resolved rosters against accounts. This is a real product decision with real upside
   (returning users skip re-upload; a corpus becomes possible) and it is the builder's call.
   It gains weight from a measured fact: a real `data.json` carries **94 distinct 12-digit
   `owner_viewer_id` values across 499 borrowed ancestor slots** — other trainers' IDs, in
   the same ID space uma.moe resolves people by. Whatever is decided applies to those too.
4. Does the corpus idea (Approach C) return later, and does publishing save-derived records
   clear privacy and ToS?
5. Retirement plan. `UmaMusumeAPI` was archived when its maintainer stopped playing, and
   `SSHZ-ORG/hakuraku` went dormant. What happens to a hosted instance here? Deciding early
   is cheaper than deciding at the end.
6. Does `master.mdb` ship inside the deploy image or mount at runtime? Unspecified, and it
   decides whether the canary's rollback is a redeploy or a file swap.
7. `IvoryTower48/Uma-affinity-optimizer` is AGPL-3.0. Reading it to cross-check base-affinity
   math carries licence considerations worth understanding *before* opening it. `hakuraku` is
   MIT and has no such problem, so prefer it as the oracle.

## Reviewer Concerns

Three rounds of adversarial review ran (5/10 -> 7/10 -> 7/10, 41 issues raised, 38 fixed).
Round 3 verified roughly thirty factual claims against the real files and found none wrong,
which is the first time that has been true. These survive unresolved and are the implementer's
inheritance, not oversights:

1. **Relation-type labelling: RESOLVED, over-scoped by ~15x.** One query settles what an
   earlier draft called uncosted. Of 1616 types, 1332 have members; **525 have exactly one
   member and can never match**; 697 are two-member bonds whose label is just the pair,
   derivable from `card_data` + `text_data` category 6. **Only 110 types have three or more
   members** — the entire hand-curation surface. Points: 1432 worth 1, 146 worth 2, 28 worth
   8, 10 worth 7. All 28 eight-pointers are 1- or 2-member bonds. The ten seven-pointers
   (`2901-2904, 3001-3004, 3101, 3102`, 5-64 members) are the region and running-style
   families and are the ones worth naming. Roughly a morning's work.
2. **Committing `master.mdb` row slices redistributes game data.** M1 is careful about the
   save-derived half and silent about this half, while Open Question 3 treats exactly that
   question as unresolved for Approach C. Settle it before the first commit of `fixtures/`.
3. **Premise 1's `breeding-optimizer` inventory is unverifiable** — closed source, no public
   API. It rests entirely on the builder's own use of the tool. Flagged as the boundary of
   verification, not as a defect.
4. **Held scope against the outside voice, twice; the arguments are recorded, not lost.**
   It argued M4-M6 should be deleted (each re-implements a `hakuraku` file already read, while
   feature parity is an explicit non-goal), and that the NestJS backend is a preference that
   manufactures Open Questions 3 and 5 plus the canary's rollback gap, since `hakuraku` ships
   an 80 KB browser payload where this plan assumes 16 MB must live on a server. Both
   arguments are sound. Both were settled by the builder before this review, and HOLD SCOPE
   means neither was reopened. Revisit deliberately or not at all.
5. **MIT attribution is an obligation and is currently unmet.** Porting `VeteransHelper.ts`
   requires shipping `hakuraku`'s `LICENSE` and copyright notice; README's Credits does not
   name `hakuraku` at all. Fix before the first ported line lands. The port also crosses an
   ESM/CJS boundary (hakuraku is Yarn 4 + `"type": "module"` + Vite; NestJS/Jest is CJS by
   default) and is bound to a `UMDatabaseWrapper` module singleton and a protobuf shape —
   `saddle.raceInstanceIds` as an array where `master.mdb` has `race_instance_id_1..8`
   columns. The translation harness must fake all of that, not just remap `ExplainRequest`.
6. **Four rounds of prior-art error, three of them structural rather than factual.** The
   failure mode migrated from inferring repo metadata, to inferring which repos exist, to
   inferring a file's directory from its page name. The habit that catches this is opening
   the thing, and it caught the largest finding of the session (`~/Developer/hakuraku`) only
   after a reviewer forced it.

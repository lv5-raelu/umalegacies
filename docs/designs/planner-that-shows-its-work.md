## Problem Statement

Umamusume shows legacy compatibility as a ◎/〇/△ icon. That icon is the **pair total**
bucketed by `succession_relation_rank` (verified: rank 1 = 0–50, rank 2 = 51–150,
rank 3 = 151–9999), and it is not the same quantity as **Individual Affinity**, the
per-member sum that actually drives spark activation rates. The game shows neither number.

Eleven implementations were examined and all of them show the numbers. Not one shows **where a number came from** — which
succession relations matched, what each was worth, which shared G1 wins counted, and which
rule applied at which link.

**This project claims no market gap and does not need one.** Verified 2026-09-09: the
planning workflow is served by `breeding-optimizer.rappy.dev` (closed) and largely by
`ayaliz/hakuraku` (MIT, and already forked to `lv5-raelu/hakuraku`). Asked directly whether
they would still build if an open equivalent existed, the builder said yes twice — once
hypothetically, and once after being shown that it does exist and is already in their own
account. **The motivation is building it. That is the stated and sufficient reason.**
Success criteria below are written for a thing that gets finished and used, not one that
wins adoption.

## What Makes This Cool

**Every number opens.** An affinity value expands into the `succession_relation` rows that
produced it, each with its `relation_point`, plus the itemized shared G1 wins, with the rule
named. **Caveat that shapes the work: `master.mdb` has no names for relation types.** Only
`succession_relation` and `succession_relation_member` reference `relation_type`, neither
carries text, there are 1616 distinct types, and no `text_data` category comes close to that
count. A bare `relation_type 508, 8 pts, shared by these three charas` is already more than
any tool shows; a labelled `"Kanto region"` requires a community-maintained mapping that is a
dependency of this project, not a lookup. A closed calculator can be trusted, never checked; the open ones checked here all
return bare scalars and throw the reasoning away. `hakuraku`'s `calculateAffinity` returns
`number`. So did the previous implementation in this repo.

The one place provenance already exists anywhere in this space is `hakuraku`'s
`calculateRaceBonus`, which returns `{entries: [{saddleId, name, bonus}], total}`. That is
the shape, applied to one of twelve variables. This project applies it to all twelve.

## Premises

1. **The planning workflow is served, twice over.** `breeding-optimizer` (closed) ships
   roster import, Breed Optimizer pair ranking sortable by Inherited% / Run Appearance% /
   Combined%, Desire Sparks tier weighting feeding those numbers, a per-pair modal with the
   lineage tree and per-spark inspiration odds with a full-run toggle, and uma.moe Trainer
   ID import. `ayaliz/hakuraku` (MIT) ships most of the same. **No feature gap justifies
   this project and none is claimed.**
2. **Provenance is the exception.** Every implementation examined, open and closed, returns
   affinity as a scalar. The only counter-example is `hakuraku`'s `calculateRaceBonus`,
   which itemizes G1 wins. Nothing itemizes base affinity.
3. **The reason to build is that the builder wants to build it.** Confirmed twice, the
   second time with an actual MIT equivalent already in their GitHub account. Recorded as a
   preference, not defended as market logic. The same applies to hosted NestJS over a static
   build: it is what they want to write. **Server-side data handling was NOT decided here**
   and any earlier statement of a never-persist rule was the reviewer's, not the builder's.
4. **README goal 3 predates all analysis:** *"Show the reasoning, not just a verdict. Every
   number is traceable back to the relations and race wins that produced it."*
5. **Borrowed ancestors are not a blocker, and they dominate.** Measured 2026-09-10 on the
   builder's own `data.json`: **816 of 1554 ancestor slots (53%)** and **192 of 518 parent
   slots (37%)** are borrowed
   (`owner_viewer_id != 0`). Every ancestor entry carries its own `factor_info_array` and
   `win_saddle_id_array` inline, so **no roster lookup is required** to score one. Ancestors
   carry no `trained_chara_id` at all — only `card_id`.
6. **Onboarding is the ceiling and the extractor is unlicensed.** Both true; neither solved
   here.

**Superseded direction, recorded:** the predecessor doc's one demand-backed finding was
*"ranking your own roster by probability of passing a named set of white sparks."* It was
falsified on 2026-09-09 — `breeding-optimizer`'s Breed Optimizer tab ranks pairs and Desire
Sparks weights them by wanted sparks. Its "no build is recommended" outcome is reversed
here on the grounds in premise 3, not on a rediscovered gap.

## Domain Model Corrections

Five errors found in review. Four would have shipped as bugs. The fourth (`card_id`) is
future-proofing: zero of the 62 distinct `card_id`s in this `data.json` are affected, so it
is a trap avoided rather than a bug caught.

1. **Seven base affinities, five bonus affinities — not seven of each.** Bonus affinity is
   +3 per G1 shared between two members that have both raced. The trainee has not raced, so
   the two trainee↔parent links carry a base term only. A uniform 7×{base,bonus} tree
   produces two nodes that can never be non-zero.
2. **`relation_point` lives in `succession_relation`, not `succession_relation_member`.**
   Verified schema: `succession_relation(relation_type, relation_point)` and
   `succession_relation_member(id, relation_type, chara_id)`. A provenance record citing
   only the member table shows membership and not the number's origin, which is the whole
   product.
3. **`succession_relation_member.id` is an arbitrary surrogate and `master.mdb` has no
   version table** (checked all 416 table names). Cite the natural key
   `(relation_type, chara_id)` plus a SHA-256 and extraction date of the `master.mdb` used.
   A cited `rowId` silently rots when a patch renumbers rows.
4. **`card_id` → `chara_id` must go through `card_data`.** The roster and every ancestor
   carry `card_id` (e.g. `101601`); relations key on `chara_id` (`1016`). `id // 100` holds
   for 100 of 102 cards and fails on two (`9100101`→`1001`, `9101101`→`1011`). Join, do not
   divide.

Names come from `text_data` where `category = 6`; its key column is literally named
`index`, a SQL reserved word that must be quoted in every query (`SELECT text FROM text_data
WHERE category = 6 AND "index" = ?`). Win-saddle names are `category = 111` (184 rows, keyed by `single_mode_wins_saddle.id`, and they are epithets like `Classic Triple Crown` rather than race names). The ◎ threshold is
`succession_relation_rank.rank_value_min = 151`.

5. **Incomplete lineages exist but are not in this roster.** The friend's export had one
   (`8361`); the builder's real roster has **zero** — all 259 entries are six-member
   complete. The nullable grandparent tuple stays (the game permits it) but it now has **no
   natural test case**, so `base.absent_ancestor` needs a synthetic fixture. Do not detect
   it via `succession_num`, which is 0 on lineages that are complete.

## Recommended Approach

**B**, with the provenance spine first. The keystone is a type, not a screen:

```ts
// NodeKind is DERIVED, not transmitted: ruleId.split('.')[0]. Eng review Issue 4 removed
// `kind` and `ruleText` from the wire type — both were derivable from ruleId and could
// disagree with it, on tens of thousands of nodes.
type NodeKind = 'total' | 'individual' | 'link' | 'base' | 'bonus' | 'row';

interface Citation { label: string; url?: string; quote?: string }  // link out, quote inline, or both

interface MasterRef {
  table: 'succession_relation' | 'succession_relation_member' | 'single_mode_wins_saddle'
       | 'succession_relation_rank' | 'card_data' | 'text_data';
  key: Record<string, number>;   // NATURAL key, e.g. { relation_type: 3, chara_id: 1016 }
  columns: Record<string, number | string>;
}

type RuleId =
  | 'total.pair' | 'individual.member' | 'link.pair'
  | 'base.two_way' | 'base.three_way' | 'bonus.shared_g1'
  | 'row.relation' | 'row.saddle'
  | 'base.absent_ancestor' | 'bonus.absent_ancestor'
  | 'base.self_link';   // ADDED IN M1, see note below

type Resolution =
  | { ok: true }
  | { ok: false;
      reason: 'unknown_chara' | 'unknown_card' | 'unknown_saddle' | 'no_relation_rows';
      id: number };

interface ExplainNode {
  ruleId: RuleId;                // THE single discriminant. kind and display text derive
                                 // from it client-side (RULE_TEXT[ruleId]), so they cannot
                                 // drift out of sync with the rule they describe.
  label: string;                 // "Trainee <-> Parent A", "Kanto region", "Yasuda Kinen"
  value: number;
  citation?: Citation;
  sources: MasterRef[];
  children: ExplainNode[];       // INVARIANT: value === sum(children.value) when non-empty

  // CEO review Issue 1: a 0 from "they share nothing" and a 0 from "I could not
  // resolve this id" must never look alike. This product's whole claim is that a
  // number opens; an unexplained 0 opening onto an empty drawer inverts it.
  // Optional (eng review Issue 4): only leaf lookups can fail to resolve. Absent
  // means "no lookup happened here", which is not the same as ok:true.
  resolution?: Resolution;
}

interface AncestorRef {
  cardId: number;                // ancestors carry card_id only, never trained_chara_id
  winSaddleIds: number[];        // MATCH ON THESE RAW IDS. Do NOT normalise to group_id:
                                 // the same race at a different racecourse is a DIFFERENT
                                 // win (JBC Classic, Takarazuka Kinen). group_id looks like
                                 // a matching key and is not. Verified 2026-09-10.
}

interface ExplainRequest {
  traineeCharaId: number;                    // chara_id from card_data; the trainee has not raced
  parents: [AncestorRef, AncestorRef];                                  // position_id 10, 20
  grandparents: [AncestorRef | null, AncestorRef | null,
                 AncestorRef | null, AncestorRef | null];               // 11, 12, 21, 22
  masterHash?: string;           // OPTIONAL echo of GET /master/meta, for staleness detection
}

interface ExplainResponse {
  pairTotal: ExplainNode;        // kind 'total'; 7 base + 5 bonus; drives the icon rank
  individualAffinity: {          // kind 'individual'; 4 links per parent, 1 per grandparent
    [positionId: number]: ExplainNode;
  };
  relationRank: {                // the icon verdict opens too, but it is a LOOKUP not a sum,
    value: number;               // so deliberately NOT an ExplainNode: value 3 with children
    ruleId: 'rank.lookup';       // summing to 337 would break the sum invariant
    sources: MasterRef[];        // cites the succession_relation_rank row
  };
  rankBounds: { min: number; max: number };   // that row's rank_value_min / rank_value_max
  masterHash: string;            // authoritative; the server owns master.mdb
}

interface ErrorResponse { code: string; message: string; field?: string }  // README: 400, never 500
```

**`base.self_link` was added during M1 and is an eleventh rule id.** The doc
shipped ten. CEO review Issue 1 requires that a 0 from "they share nothing" never
look like a 0 from "I could not resolve this id"; a suppressed self-link is a
*third* kind of zero, and without its own id fixture 5774's entire diagnostic
signature is invisible in the rendered tree. hakuraku implements the same rule by
substituting an empty relation set (`VeteransHelper.ts:188`), which produces the
correct number and no explanation, which is exactly the gap this project exists
to close.

**G1 matching rule: RAW saddle id. VERIFIED EMPIRICALLY 2026-09-10 against
`breeding-optimizer`.** Two ancestors share a G1 only if the **same
`single_mode_wins_saddle.id`** appears on both. `group_id` is **not** a matching key.

`master.mdb` records some races under several ids sharing a `group_id`, differing by
racecourse (7 such groups). Those are **different wins**: JBC Classic at one host track and
JBC Classic at another do not count as shared. The builder confirmed in game that JBC
Classic genuinely runs at different racecourses.

**How it was verified.** Trainee Special Week; parents the builder's Inari One
(`rank_score 18911`) and Tamamo Cross (`rank_score 23400`). Inari One is the rare veteran
whose *both* grandparents diverge between the two readings, giving two independent
discriminators plus two controls on one screen:

| grandparent | raw predicts | group predicts | reported |
|---|---|---|---|
| Inari One -> Gold Ship | **79** | 82 | **79** |
| Inari One -> Oguri Cap | **76** | 79 | **76** |
| Tamamo Cross -> Nishino Flower | 15 | 15 | **15** |
| Tamamo Cross -> Taiki Shuttle | 17 | 17 | **17** |

`breeding-optimizer` selected raw on both discriminators and matched on both controls.
`hakuraku` agrees, though its agreement carries no information — its
`countSharedG1RaceWins` intersects raw ids by construction, so it could not have said
anything else.

**Three positions were wrong before this test, and the record matters more than the
result.** README's original rule (deduplicate within one ancestor's wins on `group_id`) is
dead code that fires zero times. This document then claimed multiple ids meant the same race
in *different years* — falsified by Arima Kinen having one id while Classic-only Satsuki Sho
has two. Re-framed as venue variants, the builder and this document concluded twice from
memory that the race *name* was the identity. **The empirical test was available the entire
time and settled it in one message.** Ask the tools before asking anyone to remember.

**Consequence: there are now ZERO deliberate divergences from the oracle.** `hakuraku` is
correct on G1 matching and correct on the self-link rule. The translation harness becomes a
straight equivalence test rather than a differential one, and an earlier draft's claim that
"hakuraku is wrong here" is withdrawn.

**Still worth encoding as a gotcha:** `group_id` looks like a matching key and is not.
Anyone reading `single_mode_wins_saddle` will find seven groups holding the same race name
under several ids and reach for normalisation. Comment the intersection to say why it does
not.

**Self-link rule: a grandparent that IS the trainee loses its BASE term only. VERIFIED
2026-09-10 against two independent implementations.** When a grandparent's `chara_id` equals
the trainee's, the three-way base term for that parent-grandparent link is **0**; the G1
**bonus term survives intact**. `hakuraku` is correct here — `calculateGrandparentAffinity`
empties the grandparent's relation set, which zeroes base and leaves bonus alone.

**How it was verified — the project's first external validation.** The builder read four
Individual Affinity values off `hakuraku` and `breeding-optimizer` for a Gold Ship trainee
with their Mejiro Dober (`rank_score 18998`) and Narita Brian (`rank_score 17666`) as
parents. Both parents carry a Gold Ship grandparent (the self-link case) and an Inari One
grandparent (the control):

| grandparent | our base | our bonus | no zeroing | base zeroed | whole zeroed | reported |
|---|---|---|---|---|---|---|
| Dober's Inari One | 15 | 36 | **51** | 51 | 51 | **51** |
| Brian's Inari One | 24 | 51 | **75** | 75 | 75 | **75** |
| Dober's Gold Ship | 15 | 33 | 48 | **33** | 0 | **33** |
| Brian's Gold Ship | 35 | 48 | 83 | **48** | 0 | **48** |

Four for four. The controls confirm the base and bonus arithmetic against outside
implementations; the self-links discriminate all three readings and select base-only.

**Two earlier positions were wrong and are recorded as such:** the builder's recollection
that "their affinity becomes 0", and this document's assumption that the whole link zeroes.
The 33 and 48 visible in game *are* the surviving bonus.

**There are therefore ZERO deliberate divergences from the oracle.** An earlier draft
claimed two, then one. `hakuraku` is correct on both rules.

Measured on the real roster 2026-09-10: the rule changes `pairTotal` on **66 of 259
lineages (25%)**, by **13 to 65 points, median 24**, and flips the icon rank on 2.

**Caveat on what this validation did NOT settle:** bonus is identical under group and raw
matching for all four pairs above (36/36, 33/33, 51/51, 48/48), so this test does not
exercise the G1 rule. That one still rests on the builder's play knowledge alone.

**Resolution rules.** An id the *caller supplied* and the server cannot resolve is a `400`
naming the offending id, per README's validate-at-the-boundary convention. An id found
*inside* otherwise-valid data (an ancestor's unknown `win_saddle_id`, a chara with zero
relation rows) renders an in-tree node with `resolution.ok === false`, never a bare `0`.

**One resolver, not three.** `card_id -> chara_id` must go through a single `charaIdFor()`
that joins `card_data`. hakuraku inlines `Math.floor(card_id / 100)` in at least three
functions; porting that shape means fixing Domain Correction 4 in three places and missing
the third.

**A null grandparent** kills both a base and a bonus term, so it contributes *two* zero
nodes (`base.absent_ancestor`, `bonus.absent_ancestor`) and the invariant holds.
`individualAffinity` still emits keys 11/12/21/22 with value 0 rather than omitting them, so
box browse can render a uniform six-slot tree. No lineage in the current roster needs it, so
it is guarded by a synthetic fixture only. Detect an absent ancestor by
`succession_chara_array` position coverage, **never** by `succession_num`.

**`pairTotal` and `individualAffinity` reconcile exactly, and the identity is a required M1
assertion.** Every link is counted by both of its endpoints except the two trainee-parent
links, which have no trainee-side individual, so:

```
sum(individualAffinity) === 2 * pairTotal - base(T,10) - base(T,20)
606                     === 2 * 337       - 33         - 35
```

Verified across all 259 complete lineages in `data.json`: zero violations. This is the
cheapest correctness check in the design and it needs no oracle. (An earlier draft of this
document told the implementer *not* to cross-check them, on the strength of noticing
606 != 337 and stopping there.)

**Routes.** `GET /master/meta -> { masterHash, extractedAt, bootChecks }` (M0; how a client
obtains the hash *before* issuing a request, since the response also returns it), `POST /affinity/explain` (M1), `POST /roster/resolve` (M3), and a
and **`GET /roster/summary` (M3)** — eng review Issue 6.

**Box browse asks for summaries, not trees.** A full batch explain over 260 lineages is
tens of thousands of leaf nodes and tens of MB on the opening screen of the first release
anyone can use. **Note the earlier 62,500 estimate double-counted:** roughly half of it was
`individualAffinity` re-nesting subtrees `pairTotal` already contains. That doubling still
applies to every single-lineage drill-down, so having `individualAffinity` reference node ids
rather than re-nest is a second, independent win worth taking. `GET /roster/summary` returns one row per lineage — trainee name and
`card_id`, `pairTotal`, `relationRank`, and the six `individualAffinity` numbers — with no
nodes and no `sources`. Clicking a row calls `POST /affinity/explain` for that one lineage.
Provenance is a drill-down, not a list view, and this is what the access pattern actually
is.

**The signature of the self-link rule is `base['10-12'] === 0` and `base['20-22'] === 0`
with their bonus terms non-zero.** Drop the rule and `pairTotal` goes to 443. Zero the whole
link instead — a mistake an earlier draft made — and it drops further.

**Coverage gaps needing synthetic fixtures**, since no roster lineage reaches them:

- **A `group_id` regression guard.** Raw matching is correct, so build a synthetic pair where
  one ancestor holds saddle 18 (Satsuki Sho, Nakayama) and the other holds 155 (Satsuki Sho,
  Tokyo). Correct behaviour is **no shared G1, bonus 0**. Anyone who "helpfully" normalises to
  `group_id` breaks this test immediately.
- **Absent ancestors.** The real roster has **zero** incomplete lineages, so
  `base.absent_ancestor` / `bonus.absent_ancestor` have no natural test case at all.

The committed slice must carry rows for both fixtures plus the synthetic ones. It is no
longer sized for one lineage.

### Correctness oracle, with its caveats

`hakuraku`'s `src/data/VeteransHelper.ts` (MIT, on disk) is the reference. It is **not**
directly runnable against this project's inputs, and pretending otherwise would produce
false failures at M1:

- **Different data source.** It loads a bundled `data/umdb.binarypb.gz` snapshot, not this
  `master.mdb`. The same objection that demotes `breeding-optimizer` to a secondary check
  applies to it.
- **It derives `chara_id` as `Math.floor(card_id / 100)`** — the thing Correction 4 says not
  to do. Harmless on this data (0 of 62 card_ids affected), but it means the oracle and this
  implementation can diverge on a card neither has seen.
- **It does not dedupe G1s on `group_id`;** it uses a race-instance-ID range heuristic
  because the bundled snapshot omits grade fields. Both rules select the same 47 saddles,
  and both intersect on raw ids, which is the verified-correct rule. Its selection heuristic
  and this project's `win_saddle_type = 3` filter pick the same 47 saddles, so the two agree
  on both selection and matching.
- **Incompatible signature.** It takes full `Veteran` records and reads a parent's own
  `succession_chara_array` for the race bonus; `ExplainRequest` passes flat `AncestorRef`s. A
  translation harness is needed and is part of M1's scope.
- **The `gpCharaId === targetCharaId` behaviour is CORRECT, not a quirk to tolerate.**
  Verified 2026-09-10 against `hakuraku` AND `breeding-optimizer` on four Individual Affinity
  values (see the self-link rule above): the base term zeroes, the bonus survives, and both
  agree with this engine to the point. It affects **66 of 259 lineages (25%)**. Replicate it
  deliberately. Agreement here is genuine rather than circular, because two independent
  implementations were checked.
- **The G1 matching rule is NOT a divergence.** `hakuraku` matches raw saddle ids and is
  correct — verified empirically 2026-09-10 (see Recommended Approach). The harness is a
  straight equivalence test: any disagreement anywhere is a bug in the port.

**How to actually call the oracle**, since `hakuraku` has no pair-total function and no rank
bucketing at all:

```
calculateAffinity(p1, T) + calculateAffinity(p2, T) + calculatePairAffinity(p1, p2) = pairTotal
```

`relationRank` has no oracle beyond `master.mdb` itself.

**A cheaper oracle exists and should be used first.** Both `hakuraku` and
`breeding-optimizer` display **per-grandparent Individual Affinity** in their UI. Reading
four numbers off a screen validated this engine's base and bonus arithmetic and settled the
self-link rule in one pass — no harness, no ESM boundary, no hand-populated singleton. Do
that before building the translation harness. The harness is for breadth, not first
contact.

**M1 passes when** this implementation and `hakuraku` agree *given the same relation and
saddle tables extracted from this `master.mdb`*, and the fixture matches the golden numbers
above. `breeding-optimizer`'s reported number is a tertiary sanity check only.

  **Sparks are three named slots and a bag.** Across all 1,554 ancestors in the roster,
  `succession_factor.factor_type` distributes as: type 1 (blue) 1,554, type 2 (pink)
  1,554, type 3 (green) 1,514, types 4/5/6 (white skill/race/scenario) 14,184.
  **Every ancestor carries exactly one blue, one pink and one green.** All the variance
  is in the whites, 12 to 19 per ancestor. Competing tools read as cluttered because
  they render ~15 sparks as one uniform list, which hides that three of them are
  structural and guaranteed.

  Blue sparks are omitted from the summary whenever they compute to 100%, which they
  do for every parent and most grandparents: a guaranteed row is not information.
  hakuraku drops category 1 unconditionally; showing it when it falls below certain is
  strictly better, since a low-affinity grandparent's blue is a real variable.

  So the node renders four lines: the blue, pink and green named with their star count,
  always in that order and always present, then the whites as a **count only**. No summed
  star total: a sum across a bag of unrelated whites is not a quantity anyone acts on,
  and it invites comparing two ancestors on a number that means nothing. The pattern is identical on all six nodes, so it is learned once and thereafter
  only the values change. Selecting a node opens the full list: the three as prominent
  cards, then whites grouped race / skill / scenario, each with its own count. Individual
  sparks keep their own star level, which is a real quality difference; only the
  aggregates are dropped. `succession_factor.rarity` is the star count, 1-3 (README gotcha).
  `succession_factor` is not yet in the extract's table list and must be added.

  **Lineage-wide spark summary, and the odds question (design review, 2026-09-11).**
  A per-node spark list cannot support the decision, because the decision is about
  the lineage as a whole. Measured on fixture 5531: **52 distinct sparks across the
  six ancestors, and 30 of them sit on more than one ancestor** (`Leap Forward` is on
  all six). A per-node view shows that spark six separate times and never answers
  "what can this lineage give me".

  So M2 gains an always-visible summary: one row per distinct spark, grouped blue /
  pink / green / white-race / white-skill / white-scenario, sorted by chance
  descending, each row showing which of the six slots carry it.

  **The odds are M5 pulled forward**, because the summary is a list of names without
  them. Per ancestor the README's documented formula applies: `base rate x (1 +
  that ancestor's Individual Affinity / 100)`, capped at 100%, then `1 - (1-p)^2`
  for two inspirations per career.

  **The combining rule is settled against hakuraku's source (2026-09-11).** It is a
  Poisson-binomial over the carriers within ONE inspiration, then squared for the two
  a career gives: `p0 = product(1 - p_i)`, `atLeast1 = 1 - p0^2`. hakuraku's
  `SparkProcModal` computes exactly this, and it also yields `atLeast2` from
  `p1 = 2*p0*dp1`, which is worth showing because a doubled spark stacks. This project
  first implemented `1 - product(1 - career_i)` with the doubling applied per carrier;
  the two are **algebraically identical** (verified to 1e-16 over random inputs), so no
  number changed. Still an independent implementation and not the game, so an in-game
  check remains wanted, but it is no longer an unsupported guess.

  **A parent's Individual Affinity includes the parent-parent link. Verified against
  both oracles, 2026-09-11.** On the Oguri Cap verification lineage, breeding-optimizer
  reports Mejiro Dober 127 and Narita Brian 166 where this engine reports 186 and 225.
  Both differences are **exactly 59**, which is the parent-parent link (base 26 +
  bonus 33). Every other number agrees: the four grandparents and the 352 pair total
  match all three implementations.

  These are two different, both-legitimate quantities, and hakuraku computes both:
  `calculateAffinity(parent, target)` is the 127-style figure (trainee-parent plus the
  two three-way grandparent terms) and is used only for display panels and the sort
  key, while `calculateIndividualParentAffinity` adds `calculatePairAffinity` to give
  the 186-style figure. **`SparkProcModal` feeds the 186-style figure into
  `calculateSparkChance`.** So for spark odds this engine's number is the right one;
  breeding-optimizer is displaying the other quantity under an unqualified "affinity"
  label. Do not "fix" the engine to match it.

  **Blue caps for parents and not for grandparents.** A 1-star blue needs Individual
  Affinity >= 43 to reach 100%; 2-star needs 25; 3-star needs 12. Measured across all
  259 lineages: parent slots have median IA 138 and fall below the 1-star threshold
  **0.4%** of the time, while grandparent slots have median IA 36 and fall below it
  **61.8%** of the time. So parent blues are effectively guaranteed and grandparent
  blues are a real variable. **Fixture 5531 is not representative for odds**: its
  grandparents sit at IA 76-80, roughly double the roster median, which is why every
  blue in it caps. Any odds fixture needs a second lineage with ordinary grandparent
  affinity.

  **Edges show base and bonus, not the link total (design review, 2026-09-10).**
  A connector renders two numbers: `base` and `+bonus`. The link total is
  deliberately absent. It is derivable (the two parts sum to it) and it competes
  with the numbers that carry meaning: base is fixed by which two characters these
  are, bonus is what you can go and earn. Three numbers on a connector also crowd
  the edge label enough to force collisions where edges converge on a parent.

  **Relations show a total, races show names (design review, 2026-09-10).**
  `master.mdb` holds no name for any of its 1,616 relation types, and only **8% of
  the relation rows a reader actually meets** can be derived from character
  attributes: `3201`-`3206` map exactly to birth month (100% pure) and `28xx` to
  birth year, while `2901`-`2904` correlate with `card_data.running_style` at 80-89%
  and remain a hypothesis. The six most frequently seen relations are all
  underivable — `3101` alone appears 1,718 times across the roster.

  So the base term renders as a count and a total (`5 shared succession relations =
  18`) with **no expander**, and the bonus term keeps every race name and stays
  fully expandable. This is not a consolation. Base affinity is a fixed property of
  which two characters these are: the number informs which parents you pick, the
  reason never can. A shared G1 is something you can go and race for. **Detail
  belongs where a decision lives.** Note the earlier idea of substituting group
  membership for a name was tested and dropped: the first members of every large
  group are the same low-id characters, so three different relations all render as
  "shared by ~50 characters incl. Special Week, Silence Suzuka, Tokai Teio".

  The rule behind the table: **absent is a fact and reads calm; unresolved is a
  defect and reads loud.** Collapsing them into one grey `0` is the failure CEO
  review Issue 1 named, and it silently contradicts the invariant M1 tests.

  *Architecture.*
  1. **No body-size limit on the roster route.** Builder's call. The save is
     5,283,444 bytes and the global JSON limit is 256kb; even stripped to only
     what M3 reads it is 363kb, so no reasonable slimming fits. **Before any
     deploy**, revisit: an unbounded body on an unauthenticated route is a
     memory-exhaustion vector, and the outside voice argued for
     bounded-but-larger scoped to this route.
  2. **The server composes; the client never builds an ExplainRequest.**
     `POST /affinity/explain-pair` takes `{traineeCharaId, traineeCardId,
     veteranA, veteranB}` where each veteran carries its own three-slot package.
     Measured at **772 bytes**, against 5,745 for a composed ExplainRequest.
     `lineageFromPair` is lifted out of `scripts/build-fixtures.mjs` into
     tested source, and the fixture builder then consumes that same code
     instead of its own copy.
  3. **The upload's own error paths ship with it**, closing part of the
     ten-error-path deferral recorded above. An unknown `card_id` is a
     **row-level** failure, not an upload-level one: that veteran is marked
     unresolved and the other 258 stay usable, with a banner naming how many
     failed and pointing at the extract rebuild. A patch that adds one uma must
     not brick the roster during the window before re-extraction.
  4. **`ExplainRequest` gains `traineeCardId`.** A card is a costume and costumes
     carry different unique skills. It changes no computed number -- the trainee
     shows no sparks -- but it is the difference between the tree drawing the
     costume you are training and the base one. The picker therefore **labels
     costumes**: 66 characters span 105 cards, so an unlabelled list shows
     "Oguri Cap" twice, identically.
  5. **`lineageFromPair` composes missing ancestor slots as `null`** rather than
     throwing. The engine already models absent ancestors deliberately
     (`base.absent_ancestor`, the dashed empty-slot node), so rejecting a veteran
     for a missing parent would contradict the engine and refuse usable data.
  6. **The `/roster/resolve` response shape is specified explicitly**, naming
     which save fields are retained and which are guaranteed stripped. That
     response is what actually enforces parse-and-discard, so leaving it implicit
     would leave the privacy claim unenforced.

    exactly what a lift-and-reuse refactor breaks.

  stable public id, so the URL must encode the whole lineage: 6 x (`card_id` +

  versioned codec, and **a shared link embeds save-derived data**, which no server-side
  policy can cover because the sharing happens outside the server. Say so next to the share
  button whatever the data-handling decision turns out to be.

- **M7 — The borrow search.** *Documented 2026-09-15, not scheduled.* Requested by the
  builder's friends; the largest missing feature in `breeding-optimizer`.

  **The inverse query.** M1-M5 answer "given this lineage, what do I get?". This answers
  "given what I want, which lineage gets it?". The user states the sparks they want to
  inherit and the tool finds the parent pair that delivers them, from their own veterans
  and optionally from borrowable veterans on uma.moe.

  **The unit of choice is a package, not an ancestor.** Picking a veteran as a parent also
  fixes that veteran's own two parents as the grandparents: a veteran is an indivisible
  three-slot package. The user is not choosing six ancestors, they are choosing **two
  packages of three**. Half A is slots 10/11/12, half B is 20/21/22.

  **Borrowing replaces exactly one package.** A borrowed veteran supplies parent B and
  grandparents B1 and B2. Half A is always the builder's own. This is what makes the
  two-stage search the builder described correct rather than merely convenient: pick the
  best own package first, then search the borrowable pool for the complement that both
  covers what half A lacks and reinforces what it already has.

  **Two constraint scopes, and the second is grounded in mechanics.**
  - *Lineage-wide*: a star total across all six ancestors. "12 Stamina" means twelve stars
    of Stamina anywhere in the lineage, e.g. 2 stars on each of the six.
  - *Direct parents only*: a requirement pinned to slots 10 and 20. This exists because a
    parent's spark is far likelier to be inherited than a grandparent's: measured across
    the roster, parent Individual Affinity has median **138** against a grandparent median
    of **36**, and the activation rate is `base x (1 + IA/100)`. A 2-star Medium on a
    parent is worth materially more than the same spark on a grandparent, so the user must
    be able to demand it *there*.

  **Hard versus soft, and this asymmetry is the feature.**
  - Blue, pink and green filters are **requirements**. Unmet means no match, and the user
    is told so plainly and expected to relax them. That loop is the main path, not an
    error state: on the builder's roster, "Stamina >= 12 AND Medium >= 4" is satisfied by
    **25 of 33,411** own-pairs, 0.07%.
  - White filters are **never requirements**. They only rank. A result that misses a
    wanted white is still a result; a result that hits more of them ranks higher.
    Rationale: there are 231 distinct white types in the roster against 5 blue and 10
    pink, so treating whites as hard constraints would return nothing almost always.

  **Search space.** 259 veterans give 33,411 unordered own-by-own pairs, which brute
  forces in milliseconds; no index or solver is needed for the own-only case. The
  borrowable case is 259 x P where P is uma.moe's pool, and P is the part that decides
  the architecture. Own-only must therefore be a first-class mode, not a degraded one.

  **Ceilings worth encoding in the UI**, since a user can otherwise ask for the
  impossible: every ancestor carries exactly one blue, one pink and one green, at 1-3
  stars. So one blue type caps at 6 stars across the two parents, 12 across the four
  grandparents, and 18 across all six.

  Unresolved: uma.moe's API shape, terms of use and rate limits, none of which have been
  checked; how affinity enters, since the best spark match may be a poor affinity pair and
  the tool currently has no way to trade those off; and whether a veteran the user owns
  twice can fill both halves.
